# Story: Opatření a enforcing na základě identifikačních dat

## User Story

**As a** administrátor systému,
**I want** moci nastavit pravidla, jaký klient smí klíč používat, a být upozorněn na anomálie,
**so that** mohu zabránit neoprávněnému použití API klíče z neočekávaného prostředí.

---

## Context

Po implementaci E01S01 budeme mít kompletní evidenci o tom, kdo a odkud volá. Tato story přidává možnost na základě těchto dat aktivně reagovat — nastavit expected User-Agent pattern per klient, alertovat při odchylkách a volitelně blokovat neočekávané volající.

---

## Acceptance Criteria

- [ ] AC1: V admin UI lze per klient nastavit expected User-Agent pattern (regex nebo wildcard)
- [ ] AC2: V admin UI lze per klient nastavit expected MCP clientInfo name (přesná shoda nebo pattern)
- [ ] AC3: Při volání s neočekávaným UA/clientInfo se vytvoří security event v audit logu s typem `fingerprint_mismatch`
- [ ] AC4: Admin může per klient zvolit režim: `log_only` (pouze logovat) nebo `enforce` (odmítnout požadavek s 403)
- [ ] AC5: Na dashboardu/přehledu klientů je viditelný indikátor, pokud u klienta došlo k fingerprint mismatch v posledních 24h
- [ ] AC6: Existující klienti bez nastavených pravidel fungují beze změny (backward compatible, výchozí režim `log_only`)

---

## Out of Scope

- Automatické blokování na základě ML/heuristik — pouze rule-based matching
- Email/Slack notifikace (může být follow-up)
- IP-based rules (už existuje `allowed_ips`)

---

## Dependencies

- E01S01 (musí být hotové, aby existovala data pro enforcing)

---

## Notes

- Rozšířit tabulku `clients` o sloupce: `expected_user_agent` (varchar, nullable), `expected_client_info` (varchar, nullable), `fingerprint_mode` (enum: log_only, enforce, default: log_only)
- Validaci provádět v `McpFacade` po autentizaci, před spuštěním tool callu
- Zvážit, zda enforce režim má blokovat i REST API volání nebo jen MCP
