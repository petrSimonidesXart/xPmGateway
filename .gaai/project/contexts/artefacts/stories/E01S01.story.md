# Story: Rozšířený sběr identifikačních dat volajícího

## User Story

**As a** administrátor systému,
**I want** vidět u každého API volání kompletní informace o volajícím klientovi,
**so that** mohu identifikovat, odkud je API klíč reálně používán a detekovat neočekávané použití.

---

## Context

Aktuálně se do audit_log ukládá User-Agent a IP adresa. Ale MCP `initialize` handshake obsahuje `clientInfo` (name, version), který se kompletně ignoruje. Také chybí systematický sběr dalších HTTP hlaviček, které mohou pomoci s identifikací volajícího (Origin, Referer, Accept-Language apod.).

---

## Acceptance Criteria

- [ ] AC1: Při MCP `initialize` se z požadavku extrahuje a uloží `clientInfo` (name, version) a přiřadí se k danému session/klientovi
- [ ] AC2: Audit log obsahuje u každého záznamu: IP, User-Agent, MCP clientInfo (pokud je k dispozici)
- [ ] AC3: V admin UI na detailu jobu a v audit logu jsou viditelné všechny evidované fingerprint údaje
- [ ] AC4: Na přehledu klienta v admin UI je vidět souhrn unikátních User-Agentů a clientInfo, které daný klient používá
- [ ] AC5: Sběr dat nemá negativní dopad na výkon (žádné blocking operace navíc)

---

## Out of Scope

- Validace nebo enforcing na základě sebraných dat (to je E01S02)
- TLS fingerprinting (JA3) — vyžaduje změny na reverse proxy
- Ukládání plných request/response body

---

## Dependencies

- None

## Notes

- MCP clientInfo přichází v `initialize` requestu, ale tool cally jsou v samostatných POST požadavcích — je potřeba řešit vazbu session ↔ clientInfo (SSE session ID)
- Zvážit rozšíření `audit_log` tabulky o sloupec `client_info` (JSON) nebo využít existující `result_data`
