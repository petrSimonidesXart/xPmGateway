# Story: Worker pool — souběžné zpracování jobů

## User Story

**As a** uživatel systému,
**I want** aby worker zpracovával více jobů současně,
**so that** nemusím čekat ve frontě za ostatními požadavky.

---

## Context

Worker aktuálně zpracovává joby sekvenčně — jeden po druhém. Při rostoucím počtu uživatelů a automatizací se vytváří fronta, kde rychlé operace (CSV export ~5s) čekají za pomalými scénáři (~60s). Každý job si již vytváří vlastní browser + context, takže změna spočívá pouze v refaktoru poll loopu v `index.ts`.

---

## Acceptance Criteria

- [ ] AC1: Worker zpracovává až N jobů souběžně, kde N je konfigurovatelné přes env `MAX_CONCURRENT_JOBS` (default 3)
- [ ] AC2: Když jsou všechny sloty obsazené, worker nepolluje nové joby (čeká na uvolnění slotu)
- [ ] AC3: Selhání jednoho jobu neovlivní ostatní souběžně běžící joby
- [ ] AC4: Graceful shutdown — při SIGTERM/SIGINT worker počká na dokončení běžících jobů
- [ ] AC5: Logování obsahuje identifikaci slotu/jobu pro rozlišení souběžných výstupů
- [ ] AC6: Existující tooly a scénáře fungují beze změny (žádná úprava runnerů ani handlerů)

---

## Out of Scope

- Prioritní fronty / job ordering
- Dynamické škálování počtu slotů za běhu
- Sdílení browser session mezi joby

---

## Dependencies

- None

---

## Notes

- Změna se týká primárně `apps/worker/src/index.ts` (~50 řádků)
- `standaloneRunner.ts` a `scenarioRunner.ts` nevyžadují změny — každý job si vytváří vlastní browser
- RAM: ~200 MB na slot (Chromium context), při default 3 = ~600 MB
- Backend API (`getNextJob`) již podporuje atomic přiřazení — více concurrent pollů je bezpečných
